# Codex Task: Rebuild KAALI Frontend Using Saheli Safety as the UI Reference

## Role

Act as a senior frontend engineer and product designer. Rebuild the KAALI women's safety application frontend using the uploaded `Hackerwrath3.0Frontend-main` (Saheli Safety) project as the visual and product-experience reference.

The objective is to create a polished, responsive, production-minded React application that preserves the most useful UX patterns from Saheli while integrating with the **existing KAALI backend services and API contracts**.

This is an existing full-stack project. Do not start a new backend, duplicate existing services, or replace working backend functionality with frontend simulations.

## 3. Design direction: reproduce the Saheli experience, adapted to KAALI

Use Saheli as the primary reference for layout, information hierarchy, and user experience. Do not simply copy its source code line by line.

Create a distinctive, premium, calm, reassuring women's safety interface.

### Visual language

- Warm off-white or ivory backgrounds.
- Deep forest-green primary accents.
- Muted sage secondary colors.
- Restrained coral or red for emergency actions.
- Soft neutral borders, subtle shadows and generous spacing.
- Rounded cards, clear typography and readable text.
- Clean, carefully aligned icons.
- Strong contrast for safety-critical controls.
- Subtle transitions and useful loading feedback.

Avoid generic AI-generated dashboard aesthetics, excessive gradients, excessive glassmorphism, neon colors, unnecessary animations, and oversized decorative headings.

Use Lucide React only if needed for a consistent icon system. Never use emoji as a substitute for functional interface icons.

Create a responsive application layout with:

- A large interactive safety map.

## 4. Main screens and navigation

Implement the following screens using reusable React components.

### A. Safety Map — primary screen

This is the most important screen and must receive the most attention.

Include:
- Interactive MapLibre map.
- Origin and destination fields.
- Address or place selection if a compatible geocoding provider is configured.
- A button to use the current GPS position.
- A control to swap origin and destination.
- Walking-route preference.
- Route priority selection: Fastest, Balanced, Lower Risk.
- Route comparison cards.
- Distance and estimated duration.
- Risk score and risk status.
- Risk confidence, where supplied by the backend.
- Warnings and explanations supplied by the API.
- Start navigation, reroute and finish navigation controls.
- Current GPS position marker.
- Origin and destination markers.
- A clear loading, empty, error and unavailable-data state.

The map must display actual route geometry returned by the KAALI API. Never fabricate route coordinates or risk scores.

When multiple routes are returned, let the user select between them and update the map to display the selected route.

Distinguish the recommended route from other candidates without implying that any route is guaranteed safe.

### B. Route comparison

Create well-designed route cards that display the information actually returned by KAALI.

For each route, show available fields such as:
- Distance.
- Estimated duration.
- Risk score.
- Risk status.
- Risk confidence.
- Risk label.
- Warnings.
- Selected or recommended status.

Handle all risk states correctly:

- `measured`
- `estimated`
- `unknown`

If `riskScore` is `null`, show that the risk is unknown or insufficiently assessed. Do not convert missing information into zero risk, green safety badges, or a claim that the route is safe.

If confidence or supporting information is missing, do not invent it.

Clearly explain that a report-derived score is an indicator based on available information, not a probability of harm or a guarantee of safety.

### C. Live navigation

Build a usable navigation interface around the existing KAALI navigation APIs.

Include:
- Active route and selected route information.
- Current GPS marker and route line.
- Distance and ETA information where available.
- Route deviation feedback.
- Rerouting progress and result.
- A finish-navigation action.

- Network and backend failure recovery.

Use the existing navigation-session API to create and manage sessions. Send location updates according to the existing backend's rate limits and interval hints.

Do not assume a WebSocket or Socket.IO service exists. Follow the repository's implemented HTTP-based navigation flow.

Avoid sending GPS updates excessively. Clean up geolocation watchers and pending work when navigation ends or the component unmounts.

### D. Emergency SOS

Create a dedicated emergency interaction accessible from the main application.

Include:
- A prominent SOS button.
- A deliberate confirmation or activation flow that avoids accidental triggering without introducing dangerous delays.
- Current location capture, when permission is available.
- An explicit indication of the location that will be shared.
- An option to request live-location sharing when supported.
- Emergency incident status.
- Notification delivery status as returned by the backend.
- An option to retry notifications if the API supports it.
- A way to resolve or cancel an incident according to the actual backend contract.
- Clear handling of unavailable GPS, network failures and missing trusted contacts.

Use KAALI's actual SOS service, including its incident lifecycle and notification orchestration.

Generate and send the required idempotency key for SOS creation if the API requires an `Idempotency-Key` header.

Never display "SMS sent", "contact notified", or "police contacted" unless the actual service response supports that statement.

A queued notification is not the same as a delivered notification. Represent notification states honestly.

Do not invent a police-dispatch integration.

### E. Trusted Circle

Support the operations actually implemented by the backend, such as:

### G. Account and authentication

Use KAALI's existing OTP-based authentication.

Implement:

- Request OTP.

## 5. Backend integration is mandatory

The existing KAALI backend must remain the source of truth for authentication, routing, reports, navigation sessions, trusted contacts and SOS incidents.

Use the configured frontend API URL:

`VITE_API_URL=http://localhost:5000/api/v1`

Use `import.meta.env.VITE_API_URL` rather than hardcoding URLs throughout the application.

Create a centralized Axios client with:
- Base URL configuration.
- JSON request and response handling.
- Bearer-token attachment for authenticated endpoints.
- Request timeouts.
- Consistent API error handling.
- Safe handling of expired or invalid authentication.
- Typed response envelopes.

Follow the existing API envelope:

`{ data, meta }`

Follow the existing error envelope:

`{ error: { code, message, details, requestId } }`

Do not assume every endpoint returns the same status code or a non-empty response body. Handle successful empty responses, including HTTP 204 where applicable.

Read the backend's actual route files, controllers, validators and services before implementing each API call.

## 6. Routing API integration

The route request contract uses coordinate objects:

- `origin: { latitude, longitude }`
- `destination: { latitude, longitude }`
- `mode: "walking"`
- `priority: "fastest" | "balanced" | "lower_risk"`
- `maxDetourRatio`, where supported.

Inspect the validator and route service to confirm all required and optional fields.

The API returns route candidates with fields such as:
- `routeId`
- `distanceMeters`
- `durationSeconds`
- `riskScore`
- `riskStatus`
- `riskConfidence`
- `riskScale`
- `riskLabel`
- `geometry`
- `warnings`

Use the real response type and validate assumptions against the implementation.

MapLibre GeoJSON geometry uses `[longitude, latitude]` coordinate order. Do not reverse the coordinates.

Respect the returned `selectedRouteId`. Allow the user to choose another returned candidate without incorrectly treating the original recommendation as the user's selection.

If the service returns no usable candidates or an error, display a helpful recovery state rather than drawing a fabricated fallback route.

The current backend validates coordinates against a configurable pilot-area bounding box. Preserve this behavior and communicate unsupported-area errors to the user.

Do not change the MongoDB report schema, routing service, scoring logic, pilot-area configuration, or backend contracts just to make the frontend easier to build.

If the backend needs a change, document the exact gap and keep it separate from the frontend work unless the change is explicitly necessary and can be implemented without breaking existing behavior.

- Request geolocation permission only when the user initiates a location-dependent feature.
- Explain when location is being shared.
- Stop GPS tracking when navigation ends or the user revokes permission.
- Do not put sensitive location data, OTPs, private images or emergency tokens into application logs.
- Do not expose access tokens or private sharing tokens in analytics, error messages or URLs unnecessarily.
- Do not store more sensitive information in browser storage than required.
- Follow existing backend authorization and retention behavior.
- Never trust frontend checks as a replacement for backend authorization.
- Never show a green "safe" status solely because no reports exist.
- Distinguish unknown, unavailable, estimated and measured information.
- Do not fabricate emergency dispatch, contact delivery, crime statistics or safety claims.
